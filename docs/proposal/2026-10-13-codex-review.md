**1）总体判断**

两份文档可以作为方向讨论稿，但还不宜直接冻结为正式规格。v0.2 最大的问题是把“患者管理、专病数据库、药企研究服务”三个交付体系压进同一个 MVP，却没有定义数据何时足以支持某项研究、谁承担持续运营、药企实际购买什么；演示稿则容易做成页面丰富但研究逻辑不成立的展示。建议有条件通过演示立项：收敛为“一条患者管理闭环＋一个可复现的研究可行性案例”，用数据来源、质量限制和人工确认体现专业性，把疗效比较、外部对照、监管用途留在后续研究能力中。

**2）方案 v0.2 的问题与遗漏——按严重程度排序**

以下 P0 表示正式规格前必须解决，P1 表示试点范围冻结前必须解决。

| 级别／位置 | 问题与影响 | 具体修改建议 |
|---|---|---|
| **P0／§7 数据授权风险** | “无授权数据只用于内部模型调试”必须删除。内部调试仍属于数据处理，不能因不进入研究端就默认可用。 | 改成：“合法处理依据或批准用途未核实的数据隔离封存，不进入调试、训练、演示或研究；开发使用纯合成数据。”逐批登记来源、处理依据、允许用途、伦理文件、保留期及责任人。 |
| **P0／§4.1、§7 合规** | 分开勾选、脱敏、沙箱、基因数据不出境，被写成了近似完整的合规方案。实际上没有定义医院、平台、药企各自的角色及访问边界。 | 增加“主体—目的—字段—处理地点—接收方—输出—审批依据”矩阵。明确撤回后的处理、项目结束后的留存、再利用审批；跨境访问与人类遗传资源事项分别核验，不能仅以“基因数据留院”作为结论。 |
| **P0／§1、§5 证据承诺** | 从数据闭环直接跳到“监管沟通、ADC 比较、外部对照”，缺少研究问题、设计和数据适用性门槛。容易让合作方把产品功能理解成已经具备的证据能力。 | 定位改为“支持研究可行性评估与证据生成流程”。每个用例必须附一页研究卡：目标人群、研究问题、索引日、暴露、结局、随访窗、混杂因素、缺失处理、可支持与不可支持的结论。首期仅承诺描述性分析及可行性评估。 |
| **P0／§4.1 数据模型** | 把手术、放疗、新辅助、辅助和转移性治疗都归为“治疗线”，会直接污染队列筛选与后线分析；分型也被近似当成永久属性。 | 分开建模“疾病阶段、治疗意图、治疗事件、系统治疗线”。治疗线规则须版本化，并记录维持、联合、换药和中断的判定。ER/PR/HER2 保存标本部位、日期、原始结果和判读版本；派生分类不能覆盖历史结果。 |
| **P0／§4.4、§5 结局分析** | PFS、OS、复发和治疗线流失没有操作定义。“未进入下一线”可能是仍在治疗、转院、失访或死亡，不能都当作流失。 | 增加结局字典：事件证据、日期规则、索引日、末次有效随访、删失规则、判定人。区分临床记录中的进展与按研究规则判定的 rwPFS；缺少合格数据时显示“不可估计”。流失分析必须展示互斥状态及观察窗口。 |
| **P0／§4.2–4.5、§6 预警闭环** | “高风险转人工＋处置中位时长≤24小时”没有定义谁接、何时接、无人接怎么办。中位数还会掩盖长时间未处理事件。 | 定义触发、分级、分派、接单、处置、复核、关闭的状态机；设置当班责任人、超时升级和非服务时段提示。按风险层级设首响应指标，同时报告 P90、逾期未处理数；临床规则须由科室批准，不能交给模型自由判断。 |
| **P1／§3、§5 药企价值** | 医学、临床运营、HEOR 的需求被混在一个门户里。没有意向药企时，同时承诺七类用例，很难形成清晰购买理由。 | 首先选择一个委托方角色和交付件，例如“临床运营：入组可行性报告”或“医学：治疗模式与数据缺口报告”。明确项目周期、验收内容、访问方式、交付权利和费用承担方；不必现在确定价格。 |
| **P1／§6 路线图及指标** | 3000 例、500–1000 例前瞻患者和多端智能体上线，与未知的数据基础及团队能力脱节。“完整率85%”也不足以证明研究可用。 | 将日历节点改为阶段门：授权核验→样本数据审查→首个用例可计算→运营能力验证→扩大入组。完整率按研究必需字段及适用人群计算；另报抽取准确性、时间逻辑错误、结局可评估率。前瞻规模由招募速度与每例管理工时倒推。 |
| **P1／§2、§3 依据** | “已有专家”被升级为标杆医院合作；“国内证据稀薄”“药企管线最密集”等表述过满。ICH M14 也被泛化成整个研究平台的依据。 | 未取得机构授权前使用“拟合作科室”，区分专家交流与机构共建。建立来源台账，记录原始出处、日期、人群和支持的具体结论；指南推荐回到原始版本核验。M14 仅放在相应安全性研究场景。 |
| **P1／§4.1、§8 架构** | “OMOP 风格”无法验收；默认微调和物理隔离都先于需求。缺少原始证据、人工修订与分析版本之间的关系。 | 先定义原始来源层、规范化事件层、研究快照层及版本关系；每个派生字段可追溯到来源与规则。明确哪些字段映射 OMOP、哪些使用专病扩展。模型部署和微调由任务评测决定，不作为先决方案。 |

两项需要有明确依据：**去标识化不等于匿名化**，脱敏后的个人信息仍可能受个人信息保护规则约束；科研合作也不自动免除伦理审查。[网信办说明](https://www.cac.gov.cn/2024-03/22/c_1712776611649184.htm)、[国家卫健委伦理审查办法](https://www.nhc.gov.cn/qjjys/c100016/202302/6b6e447b3edc4338856c9a652a85f44b.shtml)。ICH M14 的范围是利用真实世界数据开展药品安全性评价的非干预研究，不能作为全部疗效比较或平台合规的通用背书。[ICH 官方说明](https://www.ich.org/news/ich-m14-guideline-reaches-step-4-ich-process)

**3）演示版设计的问题**

**① 故事线：当前能证明页面联动，尚不能证明研究价值。**

“患者上报症状→医生圈队列→药企看到结局”缺少关键中间环节：数据确认、研究适用性检查、项目授权和分析冻结。一次症状处置不会立即生成可信的研发证据。

建议设计成约 10 分钟、两个相连但独立的片段：

- **临床片段，约4分钟：**一名辅助内分泌治疗患者报告症状及漏服→形成待处理任务→个案管理师查看趋势和来源→记录联系、医生复核及后续随访。结束时展示“问题是否闭环、还需谁做什么”，让专家判断是否减少工作负担。
- **研究片段，约6分钟：**切换到已冻结的合成历史队列，回答“某虚构研究方案在这个数据源中有多少人符合已知条件、哪些条件无法判断”。逐步展示筛选漏斗、缺失原因、待医生核查人数及结果导出，让药企判断是否值得开展数据可行性合作。

如希望突出 ADC，应单独增加晚期患者案例，明确更换了人群和研究问题。不要让同一个演示患者在几分钟内跨越多年病程，也不要把早期随访队列直接拿去说明后线 ADC 招募能力。

**② Mock 数据：2000例和固定随机种子只能保证规模与复现，不能保证可信。**

建议采用“**专家审阅的锚点病例＋受约束的批量合成队列＋异常测试病例**”：

- 先制作约12例锚点病例，覆盖早期辅助治疗、初诊转移、复发后治疗、病理结果变化、外院治疗、失访、死亡等。
- 批量生成使用疾病状态和时间约束，不能让分期、药物、进展、死亡日期独立随机。明确数据截止日、随访窗及允许的治疗重叠。
- 保留真实数据常见的不完美：未知检测结果、缺少停药原因、晚录入、外院信息不足。明确区分“阴性、未检测、未知、不适用”。
- HER2 保存 IHC/ISH 等原始结果、标本与日期；超低表达等分类只有满足预定数据要求时才能派生。
- 用药打卡只能代表自报行为；没有处方或配药记录时，不要输出看似精确的 PDC/MPR。自拟症状问卷也不能标成标准量表。
- 每张研究图显示样本量、事件数、随访与缺失信息；小样本或事件不足时主动隐藏不可靠的估计。
- **禁止把生成器预设的“依从性改善→复发减少”画成平台发现。**合成数据中的关联只能说明计算流程。
- 病例、图表和导出文件均标注“合成数据，仅用于演示”；增加一页数据生成说明及不支持的推断。

**③ 智能体降级：只判断有没有 API key，覆盖不了现场故障。**

默认应使用**确定性演示模式**，在线模型作为可选增强。两种模式显示明确标识，共享相同业务数据和规则。

| 场景 | 应有行为 |
|---|---|
| 无 key、断网、鉴权失败、限流、超时 | 自动切换本地模板，并提示当前模式；保留当前业务状态 |
| 研究助手被问“有多少例” | 调用同一个队列计算服务，禁止模型编数字 |
| 高风险症状 | 由批准的规则触发固定提示及模拟转人工流程，不依赖模型回答是否成功 |
| 指南检索无匹配依据 | 明确说明未找到依据，不能套用相近答案 |
| 模型输出格式错误或引用不存在 | 校验失败后降级，不直接展示 |
| 用户询问改药、剂量或超出范围的问题 | 给出边界说明及医生确认路径，不执行临床操作 |

预置回答也必须引用当前病例、当前筛选条件和计算结果；不能换了患者仍输出同一段话。知识库条目应有来源、版本、适用范围和可引用位置，并核查指南内容使用权限。

**④ 技术栈：基本合适，主要问题是边界和状态设计。**

Next.js、TypeScript、Tailwind、Recharts 对这个演示范围是合理选择，当前没有理由为了架构展示增加服务数量。但需修改以下内容：

- “JSON 或 SQLite，前端直接读”不能含糊保留。**建议 JSON 保存种子数据，经服务层读取；交互状态由统一状态容器管理，支持重置。**如要求服务重启后仍保留处置记录，再使用 SQLite。
- 患者上报、医生工作台和研究查询共享同一套事件与查询逻辑，避免各页面各自维护静态数字。
- 模型密钥仅保留在服务端；分别实现提供商适配器。“OpenAI兼容”不保证工具调用、流式返回和结构化输出行为一致。
- 顶部角色切换应标成“演示视角切换”；药企视图仍只显示计划允许的聚合信息，避免演示出错误的未来权限关系。
- “不做移动端以外的性能优化”表述应重写。现场主要是桌面投屏，必须验证投屏分辨率、字号、图表密度和浏览器表现。
- 分析沙箱占位、援助项目等不能强化核心故事的入口可以隐藏；保留的占位入口必须明确说明尚未实现。

**⑤ 验收：当前标准不可重复，也不能暴露故障。**

建议将以下条目直接写入演示验收，数值属于建议目标，需在指定设备上冻结：

| 验收对象 | 可执行标准 |
|---|---|
| 启动与离线 | 按 README 完成依赖准备后，一条命令启动；无模型 key、断网均能走完整故事线 |
| 数据复现 | 相同种子、配置和生成器版本产生相同数据校验值；时间与状态硬约束违规为0 |
| 闭环状态 | 指定病例提交一次上报，只生成一条对应预警；医生处理后患者视图同步更新；关闭需有处置记录 |
| 统计一致性 | 至少5组固定筛选条件有人工核对的预期结果；页面、导出和助手计数完全一致 |
| 入组判定 | 分别展示符合已知条件、不符合、信息不足；缺失条件不得默认通过 |
| 降级测试 | 人为注入超时、鉴权失败、限流和非法输出；建议10秒内完成降级，页面无未处理异常 |
| 智能体边界 | 每个角色至少覆盖正常、超范围和缺依据问题；不得编造病例事实、统计数字或引用 |
| 演示稳定性 | 连续完成3轮完整演示并重置；无重复事件、旧筛选残留或跨轮状态污染 |

**4）正式规格前必须拍板的5个决策**

| 决策 | 推荐选择 | 对规格的直接影响 |
|---|---|---|
| **这次演示要促成什么下一步？** | 专家认可共建试点范围，潜在药企认可开展数据可行性评估 | 决定结尾交付件，避免把“平台合作、监管证据、商业采购”同时当目标 |
| **哪条临床主线、哪个研究问题？** | 默认内分泌管理闭环＋一个研究可行性案例；若明确主攻ADC药企，再另选晚期主线 | 决定患者脚本、字段、问卷、图表和入排规则 |
| **演示的真实程度到哪里？** | 纯合成数据、规则与计算真实执行、模型可选；不承诺疗效或监管适用性 | 决定哪些交互必须实现，哪些只作未来能力说明 |
| **试点由谁持续运营、谁确认数据？** | 指定科室业务负责人、个案管理责任人、数据负责人；约定服务时段及研究数据发布责任 | 没有责任人的流程不应写成可上线功能 |
| **演示技术默认路径是什么？** | 本地确定性模式优先、统一查询逻辑、可重置状态；在线模型通过适配层增强 | 决定启动方式、状态存储、断网策略和验收环境 |

**5）可以直接采纳的改进清单**

- 将“无授权数据用于内部模型调试”替换为“隔离待核验；开发使用纯合成数据”。
- 将定位中的“输出可用于监管沟通的证据”改为“支持研究可行性评估与证据生成，适用性按项目确认”。
- 给全部功能标记：**本次可交互、模拟展示、后续研究能力**，避免阶段承诺冲突。
- 为首个药企用例补一页研究卡，并据此反推最小数据字典。
- 拆分治疗事件与治疗线；补齐检测时间、来源证据、删失和未知状态。
- 增加“研究快照”步骤，阻止临床处置后研究图表无条件实时变化。
- 将入组结果从单一人数改为“符合已知条件／不符合／信息不足”，注明仍需医生核查。
- 增加一个数据缺陷导致无法回答的问题，展示系统如何解释限制及生成补数任务。
- 将三个聊天入口缩为与当前页面有关的快捷任务，避免无边界聊天稀释演示。
- 用上述验收表替换“走完故事线、回答两三个问题”，同时交付演示脚本、预期数字表和一键重置能力。
