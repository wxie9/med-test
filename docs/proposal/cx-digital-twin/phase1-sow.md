# CX 患者数字孪生首期总体架构设计与最小闭环验证

版本：首期范围收敛稿。更新日期：2026-10-21。

## 一、项目目标

完成 CX 患者数字孪生首期总体架构与核心机制设计，并由工程团队实施最小技术闭环，验证患者表示跨会话延续、上下文使用、信息更新、纠错及基础隔离能力。

采用**顾问牵头设计与技术评审、工程团队负责实施与验证**的合作方式。

## 二、工作内容

### 1. 总体架构与首期范围设计

- 梳理 CX 现有系统与数字孪生框架之间的关系，明确接入边界、依赖及待确认事项。
- 设计接入适配、患者模型、证据与长期记忆、上下文组装、助理运行时及受控更新等逻辑模块。
- 明确各模块职责、读写关系和生命周期，区分患者主体、助理身份及会话状态。
- 确定首期最小实现范围及后续扩展位置。

### 2. 核心对象与管理机制设计

- 定义患者当前表示、长期记忆和原始证据之间的关系。
- 明确已有依据、候选判断、未知及冲突信息的表达与处理原则。
- 设计来源关联、版本管理、更新提交、信息替代及失效机制。
- 明确基础身份隔离、访问权限和过程记录要求。

本项以系统机制为设计对象，暂不细化患者临床字段、具体业务规则或专用算法。

### 3. 关键流程与接口约定设计

形成四条核心流程及模块间接口原则：

| 核心流程 | 工作内容 |
| --- | --- |
| 交互读取流程 | 请求接入、身份确认、患者表示与记忆读取、上下文组装、助理输出及记录 |
| 信息更新流程 | 来源登记、候选信息产生、规则校验、记忆或状态提交、版本发布 |
| 纠错与失效流程 | 定位来源、识别直接影响、修订或失效、刷新后续使用内容 |
| 异常与追溯流程 | 处理读取失败、模型调用失败、更新失败和重复提交，记录处理状态与依据 |

### 4. 工程实施指导与技术评审

- 向工程团队说明架构、核心机制和接口约定。
- 评审约定范围内的工程实现方案，识别与设计不一致部分。
- 对实施中涉及的架构问题、接口问题及范围变化提出处理建议。
- 根据评审和验证结果修订设计，记录关键决策及遗留事项。

工程团队负责代码实现、存储配置、模型调用适配、模拟接口及运行环境准备。

### 5. 最小闭环验证与交接

- 定义验证场景、预期行为及结果记录要求。
- 指导工程团队使用抽象主体、模拟事件和接口桩开展验证。
- 审阅跨会话延续、上下文使用、更新提交、纠错失效、主体隔离及异常处理的验证结果。
- 汇总技术结论、已知限制及后续实施依赖，完成阶段交接。

## 三、阶段交付物

### 1. 顾问牵头交付

| 交付物 | 主要内容 |
| --- | --- |
| 《CX 首期总体架构与范围说明》 | 架构图、模块职责、系统边界、依赖关系、首期范围、设计假设及待确认事项 |
| 《核心机制、流程与接口约定》 | 核心对象关系、读写责任、来源与版本机制、四条核心流程、接口原则及基础权限要求 |
| 《框架验证方案与技术评审记录》 | 验证场景、预期行为、工程方案评审意见、结果审阅结论及问题处理记录 |
| 《首期总结与交接说明》 | 最终设计结论、已验证与未验证内容、已知限制、遗留事项及后续建议 |

上述内容可合并成统一文档包，不要求拆成多个独立文件。

### 2. 工程团队配套交付

**最小框架实现与验证包**包括：

- 约定范围内的源代码、配置及运行说明。
- 模拟输入、接口桩和验证场景。
- 核心流程运行记录及验证结果。
- 问题修复记录和已知工程限制。

顾问负责设计指导和技术审阅，工程成果由工程团队实施并提交。

## 四、首期范围边界

首期以**显式患者表示、基础长期记忆、单一助理运行方式及可追溯的更新闭环**为实施基线。优先采用简单、可复现的工程结构。

患者专属模型训练、复杂画像推断、知识图谱、多 Agent 协作、预测与情景推演、主动业务执行、外部系统自动回写及生产高可用等能力后置。

具体患者数据适配、业务功能和临床效果评价，在相关资料及条件具备后另行细化。本版暂不确定具体时间与费用。
