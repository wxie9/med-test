CX 数字孪生架构深度分析

v0.2 · 2026年10月21日｜患者模型、长期记忆与助理运行时分离；以证据和受控更新连接三者

首期范围说明：本页为总体参考架构。当前首期工作内容与交付物以同目录的 CX 首期 SOW 为准；本页描述的扩展能力不构成本期交付承诺。

设计建议：患者模型是跨会话延续的主体表示，长期记忆提供它的依据，助理是按任务使用这些表示的服务代理。本次将三者拆开，通过统一身份、证据引用、版本和受控更新连接，保留未来预测与情景推演的扩展位置。

分析范围是逻辑架构与职责约定。患者数据字段、入口形式、业务功能和供应商尚未确定；以下对 CX 的设计均是建议，项目原文机制集中列在证据附录。

三个核心对象项目机制患者模型长期记忆助理与上下文更新与纠错权限与关系决策与验证原文证据

患者模型 · 我们如何理解此人

  • • 按患者主体持续维护的版本化表示，包括可用事实、有限推断及未知项。
  • • 当前视图与历史版本可追溯；模型输出保持来源和不确定性。
  • • 更换 LLM、会话或助理角色，不应重建患者身份和历史。

长期记忆 · 理解依据从何而来

  • • 组织个人经历、来源声明、事实关系及其时间有效性。
  • • 记忆可被检索、纠正、撤回和失效；原始证据另行保存。
  • • 语义索引与图索引是实现选项，均不自动成为事实裁定者。

助理交互 · 当次如何工作

  • • 维护服务角色、会话状态、工作记忆与工具执行过程。
  • • 由上下文服务提供患者模型和相关记忆，不加载全部历史。
  • • 输出或工具回执先作为有类型的新事件，不直接覆盖患者状态。

两种速度 · 同一版本边界

  • • 交互路径优先及时响应；长期更新可以在后台进行。
  • • 新输入尚未被长期模型吸收时，以待处理输入显式补入当前上下文。
  • • 上下文携带模型版本、记忆进度与策略版本，避免无提示混用新旧状态。

跨层治理 · 必须由 CX 控制

  • • 区分被描述的患者、实际发言者、执行代理和会话。
  • • 授权同时覆盖写入、检索、上下文、工具、缓存与派生结果。
  • • 纠错与撤回沿证据依赖链传播，并检查异步重算是否完成。

  • • 箭头展示主要信息流；查询返回、CX 回执回流和更新门槛见下方时序与分析。
  • • 具体患者字段、数据格式、功能和供应商均留待确认。

三个核心对象与各自的生命周期

v0.1 把状态、历史、模型和编排连接成一个闭环，但没有充分说明谁拥有患者状态、谁拥有交互状态，也容易让人把长期记忆理解为存储模块。v0.2 将患者长期表示从助理运行时中抽出，并增加上下文组装与独立更新管线。

对象回答的问题生命周期与权威边界
患者模型 Patient Model此刻我们在何种依据下如何理解这个人按患者主体延续；事实锚点、当前描述、有限假设和未知项分别表达。它的版本由受控更新发布。
长期记忆 Long-term Memory发生过什么、谁说过什么、哪些信息仍有效跨会话累积，支持检索、纠正、失效和撤回。是理解依据的组织层，并不自动裁定临床真实性。
助理运行时 Assistant Runtime本次应该怎样理解请求、表达和执行按角色、会话和执行任务运行；拥有工作记忆、工具状态和服务约束。模型或助理可以替换，患者表示保持连续。
原始证据 Evidence解释和结论最终依据哪个输入版本按来源保存原文或引用、署名和修订关系；按保留及撤回策略管理。不能只留下 LLM 摘要。
任务上下文 Context本轮允许模型看到哪些信息一次任务或一轮交互的授权投影；包含必要状态、相关记忆、当前输入和策略版本，不是又一份完整患者档案。

这里的“患者模型”是一种可解释的数字表示，不等于某个 LLM，也不要求一个患者对应一个独立训练的模型。孪生实例可以由身份、版本化表示、历史依据及其可用计算能力共同构成。现阶段设计的是这种表示与演化机制；预测是否可用，要靠后续任务与证据验证。

从项目中借鉴机制，而不是拼装产品名称

参考项目一手资料支持的机制对 CX 的设计判断
Letta / MemGPT当前 MemFS：显式、分层、git 版本化记忆；与旧 v1 memory blocks 区分。原文借鉴持续存在的代理与精简上下文；患者模型由 CX 单独管理。
Second Me从原始资料、解释性表示到参数化个人模型的分层。原文保留个人上下文提供者这一角色；首期采用显式可修订表示，参数化作为后续可选路径。
Graphiti / Zepepisodes、来源、关系、时间有效性与历史查询。原文借鉴时间与证据关系；图数据库是候选实现，不预设必选。
Mem0记忆写入与检索分离，当前自动提取路径为追加式。原文应用需要自己规定冲突与事实晋升规则，不能把存储成功当成状态已确认。
Honcho持续更新的 peer representation，及不同观察者的表示。原文患者理解应是一等对象；推断与来源声明分开，也要按访问者授权生成视图。
Hindsightretain / recall / reflect 分工及派生表示的后台维护。原文归纳、摘要和模型视图应可失效和重建，后台完成状态要被观测。
OpenClaw / Hermes来源与晋升、用户模型、助手记忆和会话历史各有职责。原文把患者信息、助手经验、公共知识和临时任务状态分别管理。

Delphi、Personal AI 和 Future You 仍可用于观察个人化交互形态；本次关键决策涉及状态权威、时间、更新和隔离，因此以公开机制更清楚的上述资料作为主要证据。项目的通用记忆评测结果不能直接证明 CX 的患者建模质量。

患者模型是带证据与不确定性的当前解释

建议把患者模型定义为：在某个版本和授权范围内，对同一患者已有信息作出的组织化表示。它可以有多个视图，但都需要回到一致的主体身份、来源与版本。这里先定义表示类别，不定义病种字段。

表示类别意义更新原则
事实锚点来自指定来源、具有声明类型与确认状态的已知信息区分“有记录支持某个说法”和“该说法已被核实”；新的来源不能静默覆盖旧来源。
相对稳定的个人表示在多次交互中逐步建立的偏好、目标和背景稳定性是可修订假设；不能由单次交流固化为长期特征。
时变状态视图在指定时间窗口内系统对当前情况的描述同时表达发生时间与获知时间，支持迟到事件、历史回看与新旧状态替代。
解释与假设由模型根据证据形成的归纳、关联或推测显示其推断性质、依据、适用范围及生成版本；设定确认、过期或否定条件。
未知与冲突资料缺失、多来源不一致、尚未确认的部分保留缺口与竞争解释；不为了生成完整画像而强行补齐。

患者模型中的描述性部分，可以先实现为受控发布、可重建的视图；更复杂的行为或状态估计模型作为后续可插拔能力加入。任何学习型表示都保留其支持的输入版本和适用边界。助理可以提出新的理解，但发布到长期患者模型，需要经过独立更新规则。

患者表示、计算模型与数字孪生能力

“患者模型”描述被服务的这个人；“计算模型”是处理信息的方法，例如共享 LLM、规则、统计模型或后续机理模型。一个计算模型可以服务很多患者，一个患者表示也可以被不同计算模型读取。助理的角色与表达方式则属于第三个维度，不应与患者身份绑定。

数字孪生可逐层具备三种能力：描述当前与历史状态；估计未直接观测的状态及其变化；在明确假设下预测或比较情景。v0.2 先建立描述与演化的基础，并为后两者保留输入快照、模型版本、结果类型和反馈接口。按时间更新档案不会自然产生预测能力；LLM 能生成未来叙述，也不代表已经建立有效的状态转移模型。

因此，患者模型与长期记忆不是两份互相竞争的“真相”。记忆保留可检索的依据与历史，患者模型提供当前任务更容易使用的组织化解释；确有权威来源的结构化更新也可以直接驱动视图，不必先经过 LLM 自由抽取。

长期记忆是管理依据的服务，而不是一个向量库

建议在逻辑上区分四类内容，底层是否使用关系表、图、全文索引或向量索引后续再选。

内容角色避免的混淆
经历与来源记录保留事件顺序、原始输入的引用和谁表达了什么对话摘要不能替代来源证据；同一句话被多次召回不算多份证据。
语义与时序记忆组织可复用声明、关系、有效时间与替代关系检索相关度不是事实可信度；最新写入也未必代表最新发生。
归纳与汇总把多次经历压缩成便于使用的摘要或模式汇总属于派生表示，受源纠错和撤回影响；不能独立于证据永久有效。
个人意图与约定记录已表达或已确认的意向及其当前状态讨论过、建议过、同意了、执行了与完成了需要保持区别。

辅助的管理元信息可以先确定：关联主体、来源、时间、版本、声明或推断类型、确认状态、权限范围及派生依赖。这些是系统治理约定，不是患者临床字段。置信度若由模型生成，只能作为辅助信号，不能被解释为已经校准的医学概率。

原始证据、记忆条目、患者模型视图可以由不同服务维护，但同一逻辑信息尽量只设一个明确写入责任方。索引和摘要保持派生性质；当来源变更，系统能找到其影响范围，而非依赖下一次问答碰巧纠正。

助理通过上下文服务使用患者模型和记忆

助理负责服务角色、当次请求理解、表达、计划与受控工具调用。它拥有运行状态，但患者的长期表示不应依赖某个助理进程或一份系统提示词。助理的操作经验也不进入患者特征空间。

新增的上下文服务，是三者之间最关键的连接。它依据主体、当前发言者、角色、任务和授权，读取患者模型的适用视图，补充相关记忆与共享知识，再把当前输入和待处理变化清楚标记后提供给助理。

上下文组成为什么需要
患者模型快照为当前交互提供一致、精简的个人表示。
相关记忆与证据引用补足当前请求需要的历史细节，并允许回查来源。
本轮工作记忆与待处理输入新消息尚未进入长期模型时，当前交互仍能使用它，同时不把它伪装成已确认长期事实。
共享知识与能力说明公共内容和通用推理能力具有自己的版本与访问规则，不记成某个患者的经历。
权限、版本及处理进度说明这轮用了哪个患者视图、哪些资料以及怎样的授权；便于追溯和失效。

不要求所有存储共享一个全局版本号，但需要一个兼容的版本清单：患者视图基于哪些输入进度、记忆覆盖到哪里、是否有尚未吸收的新事件、策略版本是什么。若检索命中旧记忆与当前视图冲突，上下文服务须保留差异并按规则处理，不能把冲突隐藏在自然语言摘要里。

助理更换基础模型或上下文压缩时，长期身份与表示仍然存在。多名助理访问同一患者，也应按角色读取授权视图，不能依靠复制聊天记录来同步。

交互、长期更新和纠错分别走什么路径

打开交互与更新时序图。图示是逻辑示例；不要求每次新输入同时更新全部存储，也不要求所有更新均等待 LLM 处理。

当次交互路径

  1. CX 接入层验证身份与授权，登记输入来源及事件标识。
  2. 助理向上下文服务请求本轮所需信息。
  3. 上下文服务读取患者视图和相关记忆，加入当前输入、共享知识及版本清单。
  4. 助理生成输出或工具调用请求；执行权限与结果核验经过统一边界。
  5. 系统记录交互输出与真正收到的执行结果，保持不同事件类型。

长期更新路径

  1. 更新管线从有来源的事件中筛选可长期复用的信息。
  2. 抽取只产生候选声明；区分新增、补充、状态变化、纠错和来源矛盾。
  3. 按类型与确认要求决定写入、搁置、替代或失效；保留更新依据。
  4. 发布受影响的记忆与患者模型版本，标记依赖的源进度。
  5. 通知上下文与缓存刷新；失败的异步作业可观测、重试，重复事件不重复计算为新证据。

纠错与撤回路径

先定位源记录及其版本，再沿“源记录 → 声明 → 归纳 → 患者视图 → 缓存”检查影响范围。需要时撤销可访问性、使派生结论失效并重算。模型升级也采用类似重建路径，以区分患者本身发生变化，还是系统理解方法发生变化。

已经执行的外部动作不因记忆删除而自动撤销；已经交付的回答也不能被假定已收回。二者需要独立的业务处理与追溯规则。保留、撤回和审计之间采用明确策略；“可追溯”不意味着永久保留全部个人原文。

把主体、发言者、助理和会话分开

一次对话可能谈及患者本人，也可能包含他人转述。因此至少有四个独立的身份维度：被描述的主体、实际发言者、执行服务的代理，以及本次会话或任务。它们的对应关系由 CX 确认，不能从文本中的自称直接取得。

同一患者具有共同的身份与版本体系，不意味着所有角色看到同样的信息。权限判断需要覆盖记忆读取、患者视图、上下文拼接、工具输入输出和派生缓存；撤销授权后，相应投影也要刷新。命名空间或 user_id 过滤有助于组织数据，但必须由服务端授权保证实际访问边界。

建议明确三类写入权限：助理可以提交候选记忆和修改会话工作区；记忆服务依据规则提交条目；患者模型服务依据受控更新发布长期视图。高影响的确认规则由 CX 指定，而非交给一次 LLM 评分。

需要防止的三种循环

  • 回声变证据：助理推测先被写成摘要，下一轮又把摘要当作原始支持，反复强化同一推测。
  • 工具成功变现实成功：请求已发出或接口已接受，未经确认便被写成患者状态已改变。
  • 模拟变观察：生成的个人口吻或未来情景，被写回为患者已经表达的意愿或已发生的事件。

未来如引入预测或情景推演，应读取指定版本的患者表示，在独立分支运行，记录假设、模型版本与适用范围。模拟结果回到分析空间，实际观察回到证据空间，两者的晋升规则保持独立。

现在应确定的架构决策与验证边界

方案好处主要代价当前建议
患者信息全部绑定单个助理结构少，容易验证交互体验患者状态与代理角色、会话和框架耦合；更换代理与多角色协作困难可作局部体验原型，不作长期架构依据。
独立记忆服务，患者模型隐含在提示词中记忆可复用，接入较直接不同助理可能临时重构出不同患者理解，难以追溯当前视图可用于探索检索，但需要补足患者模型层。
患者模型、长期记忆、助理独立，受控更新连接职责清楚，支持替换、重建、并发和多角色视图增加版本协调、上下文组装和更新规则推荐的 CX 逻辑架构；部署可以先保持模块化单体。

首期不需要同时部署 Letta、Graphiti、Mem0、Honcho 和 Hindsight。它们是机制参考与候选组件；CX 先掌握身份映射、表示语义、证据依赖、权限和版本边界，再判断哪些能力适合委托给具体框架。

可在数据未知时验证的事项应观察的结果
跨会话延续与基础模型替换患者主体与长期视图保持连续，助理角色和会话工作区不串用。
单次推断与重复召回候选保持推断标识；重复使用不会被计作新的独立支持来源。
迟到、重复或矛盾事件能表达发生与获知时间；重复处理幂等，矛盾保留可解释结果。
后台更新尚未完成本轮上下文展示处理进度，并能区分当前输入与已发布状态。
来源纠正或撤回可定位派生项并确认失效及刷新范围，不能只验证删除按钮返回成功。
患者、角色及访问权限交叉读写、检索、上下文与缓存均执行一致的授权边界。
实际结果与假设分支工具回执、已确认观察和模拟输出各有类型，不互相晋升。

这些检查使用抽象主体、事件与合成内容即可验证架构性质，不证明真实患者建模准确或改善生活质量。真实数据可用后，再确定表示字段、更新频率、适用任务、预测评价和业务效果。

SOW 中可对应的阶段目标：完成 CX 患者数字孪生的总体架构及核心机制设计，明确患者模型、长期记忆、助理运行时的职责与生命周期，设计证据与版本体系、上下文组装、受控更新、纠错撤回及 CX 集成边界，并形成可用抽象事件验证的架构验收方案。
