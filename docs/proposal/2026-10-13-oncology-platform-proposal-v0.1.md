## 0. 一句话定位（待确认）

> 以"肿瘤患者全生命周期数据闭环"为底座，向上服务药企研发与商业化（真实世界证据、患者招募、上市后研究），向下服务患者与医生（随访、PRO、用药管理、康复），形成"数据 → 证据 → 服务"的双边飞轮。

这是本草案的核心假设。如果项目的真实重心是"AI 制药/药物发现"而非"数据与患者服务"，整个方案需要重构，见第 7 节的关键问题。

## 2. 对需求的理解写回

**你说的：**
- 医疗项目，方向是肿瘤/癌症
- 两条主线：治疗制药 + 患者全生命周期管理
- 先调研，再迭代方案

**我的假设（请纠正）：**
1. "治疗制药"指的是服务药企的研发与商业化环节（临床试验、RWE、上市后），而不是自己做药物发现（AI 制药）。
2. 项目主体是软件/数据平台公司，不拥有医院或药房。
3. 目标市场是中国，首期以 1–2 个瘤种在少数标杆医院落地。
4. 团队有一定的医疗合作资源（医院科室或药企 BD），否则冷启动极难。
5. 成功标准：18 个月内有付费药企客户 + 在标杆医院形成持续的患者数据闭环。

## 3. 问题定义：两条主线如何咬合

```
  药企研发/商业化                      患者全生命周期
  ┌───────────────┐                 ┌──────────────────────┐
  │ 靶点/适应症洞察 │◄── 真实世界数据 ──│ 筛查 → 诊断 → 治疗   │
  │ 试验设计/入组   │◄── 患者匹配 ─────│ → 随访 → 康复/生存期 │
  │ 上市后研究/RWE │◄── PRO + 结局 ───│ → 复发/二线 → 安宁   │
  │ 商业化/准入    │── 患者服务/PAP ──►│                      │
  └───────────────┘                 └──────────────────────┘
                 ▲                              ▲
                 └──── 合规数据底座（脱敏、授权、审计、溯源）────┘
```

价值主张：
- 对药企：更快的入组、可用于监管的 RWE、上市后真实疗效/安全性反馈。
- 对医生：减少随访与 PRO 收集的人工负担，获得结构化的患者全程视图。
- 对患者：个性化随访计划、症状预警、用药依从、试验机会、经济援助对接。
- 对保险：规范诊疗 + 院外管理降低赔付不确定性（上海申爱保模式已验证可行方向）。

## 4. 三种切入方案

### 方案 A：患者侧先行（ePRO 随访 + 全程管理 → 积累数据 → 卖证据）

- 做法：面向 1–2 个瘤种（如肺癌、乳腺癌）做院外数字化随访与 PRO 管理，先服务医院科室，形成纵向患者数据，再向药企提供 RWE 与招募服务。
- 优点：入口贴近患者与医生，数据是一手的、纵向的、含 PRO（国际标杆 Carevive 的差异化点）；团体标准正在制定，政策顺风。
- 缺点：前期无收入或靠医院项目费，周期长；医院入口被医渡云/蚂蚁等占据；冷启动依赖科室关系。
- 适合：团队有医院科室资源，能接受 12–18 个月的数据积累期。

### 方案 B：药企侧先行（RWE/招募服务 → 反向建患者网络）

- 做法：先以服务公司形态，承接药企的上市后研究、患者招募、患者支持项目（PSP/PAP），借项目预算进入医院，顺势部署患者管理工具。
- 优点：现金流早（零氪的成熟路径）；药企需求明确（ADC/双抗 III 期密集读出，上市后证据需求激增）。
- 缺点：容易做成 CRO/服务公司，数据资产沉淀慢；与零氪、IQVIA 正面竞争；患者体验不是核心。
- 适合：团队有药企 BD 资源，想先活下来再做平台。

### 方案 C：AI 智能体切入（肿瘤全病程智能体 → 医生/患者双端 → 数据闭环）

- 做法：以大模型智能体为产品形态，对接医院 HIS/EMR，院内做指南助手、分期辅助、MDT 辅助，院外做患者管家（随访、症状分诊、用药提醒），数据闭环后向药企开放。
- 优点：当前资本与医院关注度最高（中山肿瘤 CACA 助手、仁济智能体）；技术差异化空间大；一套底座两端复用。
- 缺点：医疗 AI 监管与责任边界不清；巨头（蚂蚁、京东、医渡）投入大；疗效反馈与院内外数据壁垒是公认断点。
- 适合：团队技术强、有耐心，并能找到一家愿意共建的标杆肿瘤医院。

### 推荐：A 为主、B 为现金流、C 为技术杠杆的组合

理由：
1. 患者纵向数据 + PRO 是国内尚未被充分占据的位置，且是药企 RWE 的稀缺要素。
2. 用 B 的药企项目（PSP/上市后研究）支付 A 的落地成本，避免纯烧钱。
3. C 的智能体不作为独立产品，而是嵌入 A 的随访与 B 的数据结构化环节（NLP 抽取病历、症状分诊、试验匹配），降低监管风险。

## 5. 推荐方案的产品蓝图（v0.1）

### 5.1 用户与角色

| 角色 | 核心场景 |
|---|---|
| 患者/家属 | 随访计划、症状上报（ePRO）、用药提醒、检查提醒、康复指导、试验机会、援助项目 |
| 医生/个案管理师 | 患者全程视图、PRO 预警工作台、随访任务、MDT 资料包、试验入组候选 |
| 药企（医学/市场/临床运营） | 项目看板、入组漏斗、RWE 数据集与分析、上市后安全性信号 |
| 平台运营/数据团队 | 数据治理、脱敏与授权管理、质量审计、瘤种模型维护 |
| 保险（后期） | 规范诊疗核验、院外管理履约数据 |

### 5.2 模块划分

1. **患者旅程引擎**：按瘤种、分期、治疗方案生成随访与 PRO 计划（参考 CACA/NCCN 指南与团体标准草案）。
2. **ePRO 与症状分诊**：标准量表（PRO-CTCAE、EORTC QLQ-C30 等）+ 规则/模型预警 + 个案管理师处置闭环。
3. **临床数据接入与结构化**：HIS/EMR/LIS/PACS 接口或患者上传，NLP 抽取诊断、分期、治疗线、不良事件（治疗线推断是难点，需人工复核机制）。
4. **合规数据底座**：知情同意与授权管理、脱敏分级、审计日志、数据溯源，符合 PIPL/数据安全法与 NMPA RWS 检查要点。
5. **药企服务层**：试验匹配与招募、上市后研究（PMS/PASS）项目管理、RWE 数据集交付与分析沙箱。
6. **AI 智能体层**：患者管家（院外）、医生助手（院内，指南问答、资料汇总），均为辅助性质，不做诊断决策。

### 5.3 数据流（简化）

```
患者 App/小程序 ──ePRO/依从──► 旅程引擎 ──预警──► 个案管理师/医生工作台
        ▲                          │
        │                          ▼
医院 HIS/EMR ──接口/上传──► 结构化与治理 ──脱敏授权──► 药企分析沙箱 / RWE 数据集
                                   │
                                   └──匹配──► 试验入组候选 ──► 研究中心
```

### 5.4 首期范围（MVP，建议 6 个月）

- 1 个瘤种（建议肺癌：患者量大、ADC/双抗/靶向药管线最密集、随访规范草案已有）。
- 1–2 家标杆医院科室 + 1 个药企 PSP 或上市后研究项目作为付费锚点。
- 功能：随访计划 + ePRO 周报 + 症状预警 + 医生工作台 + 基础数据治理与授权。
- 不做：自建药房、自建 AI 制药、保险产品、多瘤种泛化。

### 5.5 衡量指标

| 指标 | 目标（MVP 结束时） |
|---|---|
| 入组管理患者数 | 500–1000 |
| 周度 PRO 填报率 | ≥ 60% |
| 预警到处置中位时长 | ≤ 24 小时 |
| 结构化字段完整率（诊断/分期/治疗线） | ≥ 85%（含人工复核） |
| 付费药企项目 | ≥ 1 |

| 数据合规（PIPL、遗传资源、出境） | 患者逐项知情同意；基因组数据不出境；药企侧仅提供脱敏聚合或沙箱内分析 |
| 医疗责任边界 | AI 仅辅助与提醒，所有临床决策由医生确认；预警 SOP 明确责任人 |
| 医院入口竞争 | 以科室项目和药企预算切入，不与院内数据治理厂商正面争 HIS 入口 |
| 患者依从性 | 微信小程序低门槛、个案管理师人工触达、与随访复诊挂钩 |
| 商业闭环不成立 | MVP 前锁定至少一个药企付费项目；并行探索商保（上海模式）合作 |
| 治疗线推断等数据质量 | 人机协同复核、质量指标公开、按 ICH M14/NMPA 要求建立溯源 |
