# CX 与 DX 首期 SOW 版本二：顺序推进

统一口径讨论稿 · 2026-10-21

## 一、项目目标与共同范围

CX 完成患者数字孪生首期架构与核心机制设计，形成患者表示、证据与长期记忆、上下文使用、单一助理交互和受控更新的最小闭环。

DX 完成共用持续改进框架首期架构与核心机制设计，支持临床 Agent／工作流优化和软件开发、bug 修复两类任务，形成候选隔离执行、评估比较、人工评审及版本追溯的最小闭环。

两项目均采用顾问牵头设计、实施指导与技术评审，工程团队负责工程实现与验证，项目方负责资料与环境协调、业务／专业要求确认及阶段交付接收的合作方式。

共用文档模板、来源与版本原则、评审方法和验证记录方式；各项目保留独立的资产、权限、实施依赖和验证结论。CX 与 DX 的系统集成另列后续范围，本期不将一个项目建设完成设为另一个项目成立的技术前提。

首期概念架构分别见 [CX 数字孪生模块关系图](figures/cx-phase1-architecture.png) 和 [DX 共用持续改进底座图](figures/dx-phase1-architecture.png)。图中模块表达逻辑职责，不预设独立部署单元、具体患者字段或生产环境拓扑。

## 三、统一交付物

每个项目分别形成以下四类顾问牵头交付内容，两项目合计两套。可以整合在同一文档包中，但应保留项目标识、版本和对应证据。

| 顾问牵头交付物 | 两项目统一内容要求 |
| --- | --- |
| 《CX／DX 首期总体架构与范围说明》 | 架构图、模块职责、接入边界、首期范围、设计假设、依赖及待确认事项 |
| 《CX／DX 核心机制、流程与接口约定》 | 核心对象、管理机制、关键流程、接口原则、权限与版本约定 |
| 《CX／DX 框架验证方案与技术评审记录》 | 验证路径与预期行为、工程方案评审、过程及结果审阅结论、问题处理记录 |
| 《CX／DX 首期总结与交接说明》 | 最终设计结论、已验证与未验证内容、已知限制、遗留事项及后续建议 |

工程团队按项目分别提交《最小框架实现与验证包》，包括约定范围内的代码、配置与运行说明，最小接入或适配、抽象／模拟输入与验证用例，核心流程与异常记录、验证结果，以及问题修复、必要恢复或回退说明和已知限制。

实施过程中可共用协调与问题记录，但每个交付项需能对应所属项目及其完成状态。工程验证包由工程团队实施并提交，顾问负责设计指导和技术审阅。

## 五、统一阶段与完成依据

| 阶段 | 主要工作 | 阶段成果与进入下一步的依据 |
| --- | --- | --- |
| 阶段一：架构与范围 | 完成工作包一 | 《首期总体架构与范围说明》形成并评审，首期边界、关键依赖及待确认事项明确 |
| 阶段二：机制与验证准备 | 完成工作包二、三，准备工作包五的验证方案 | 《核心机制、流程与接口约定》和验证方案形成，约定最小工程范围与验证环境，具备对应实施条件 |
| 阶段三：实施指导与闭环验证 | 工程团队实施，顾问开展工作包四并指导工作包五验证 | 实现验证包、评审及结果记录形成；影响约定核心流程的阻断问题完成处理，其他问题有明确记录与处理安排 |
| 阶段四：总结与交接 | 完成设计修订与工作包五交接 | 四类顾问交付内容与工程验证包整理完成，已验证范围、限制和后续依赖明确，完成交接确认 |

阶段体现工作依赖，不对应固定日历或持续时长。设计修订贯穿工程验证；需要提前开展的工程准备，以相关设计和环境已具备条件为前提。

## 六、首期边界

CX 采用显式患者表示、基础长期记忆、单一助理和受控更新。患者专属训练、复杂推断、知识图谱、多 Agent、预测推演、主动业务执行、外部系统自动回写及生产高可用后置。

DX 采用共用实验管理、两类任务最小适配、固定受限探索策略和人工评审。历史回放本期完成记录与接口原则；有限实际回放作为条件具备后另行确认的扩展项，不纳入默认最小工程交付。自动探索策略优化、改进执行器自修改、模型权重训练、无人评审正式发布、大规模跨院实施、生产高可用及长期运维后置或另行约定。

本期聚焦框架与流程，不细化患者字段、具体临床业务功能或专用算法；真实数据适配、院内实际联调和生产实施另行确认。验证按实际使用的抽象任务、模拟输入、接口桩或真实接口报告层级，模拟结果不表述为临床效果或生产就绪。

两项目框架验证均关注流程、边界与可追溯性；DX 不预设每轮必须获得更优版本，任务收益与机制泛化需要独立证据。两种推进方式沿用相同首期范围和交付要求，仅调整组织与衔接。本篇保留不含时间及费用的基础范围；阶段节奏、周期估算及资源条件另见[进度评估附件](schedule-assessment.md)。

## 七、版本二：先完成一个项目，再推进另一个项目

### 1. 组织方式与顺序

将 CX 或 DX 确定为先行项目，完成其约定首期交付并确认交接后，再正式启动另一项目的首期设计与实施。先后顺序在启动安排中根据资料、环境、工程与评审资源、业务优先级确定，本稿兼容 CX→DX 与 DX→CX。

启动准备可以核对两项目的资料目录和依赖，以确定先后顺序；后续项目的实质架构设计、实施指导及工程验证在切换后开展。先行项目的资源和阻断问题按其范围处理。

### 2. 推进安排

| 推进环节 | 先行项目 | 后续项目 | 切换或进入下一步的依据 |
| --- | --- | --- | --- |
| 启动确认 | 确定范围、接口人、资源与依赖 | 仅核对基础资料与启动依赖 | 明确先后顺序及各自首期范围 |
| 集中推进先行项目 | 按阶段一至四完成设计、实施指导、验证与交接 | 保留资料和依赖清单 | 先行项目完成约定交付及交接确认 |
| 项目切换 | 明确已知限制、遗留事项及其责任 | 重新核对环境和任务条件，吸收可复用原则 | 后续项目启动条件具备，确认其设计输入 |
| 集中推进后续项目 | 按已确认责任处理遗留事项 | 按同样四阶段完成自身设计、实施指导、验证与交接 | 后续项目按自身证据完成交付确认 |

### 3. 先行项目完成与切换条件

- 四类顾问交付内容及约定工程验证包形成，并完成对应讲解与交接。
- 影响约定核心流程的阻断问题已处理；非阻断问题明确状态、责任及处理安排。
- 已验证与未验证范围、实际环境、使用的模拟或真实接口及后续依赖有记录。
- 项目方完成首期交付接收及切换确认；后续项目所需资料、人员和环境具备约定启动条件。

完成依据采用已约定的首期验证层级，真实患者资料或生产环境不属于首期约定条件时，不追加为切换前提。若先行项目因外部条件无法完成约定交付，需要明确调整范围或推进方式，再更新相关材料；不自动将其标记为完成。

### 4. 两种顺序的安排差异

| 顺序 | 可优先形成的成果 | 后续项目仍需完成的工作 |
| --- | --- | --- |
| CX→DX | 患者表示、证据、更新纠错及交互闭环的设计与验证经验 | DX 独立的任务契约、执行隔离、候选评估、发布与回退；不能直接用 CX 验证替代 |
| DX→CX | 实验管理、评估记录、版本追溯及技术评审方法 | CX 独立的患者模型、长期记忆、上下文与更新机制；不能仅凭 DX 底座视为完成 |

可以复用模板、记录方式和已确认的工程原则，仍需检查其对后续项目的适用性。前一项目的后续运维与新增需求另行明确，避免在后续项目启动后形成未界定的持续工作。
