# DX 共用持续改进底座深度分析

讨论稿 v0.2 · 2026-10-21

## 1. 项目定位与设计判断

DX 同时覆盖临床 Agent／工作流优化与代码开发、bug 修复。两类任务共用任务管理、候选隔离、实验记录、评估编排和变更审阅流程，通过领域适配器连接不同执行环境、评估标准与发布路径。

建议将项目定位为“DX 受控持续改进框架”。首期建立可复现、可比较、可拒绝、可追溯的改进闭环，以 RRSI 的搜索约束和候选选择机制为主要参考，同时建立支持 Dream-RSI 历史回放的轨迹结构。探索策略的自动优化根据历史覆盖、评估可靠性及资源条件逐步启用。

本稿是架构与工作范围讨论，不代表工程已经实施或临床效果已获验证。沿用顾问牵头设计与技术评审、工程团队负责实施与验证的分工；暂不确定时间、费用、患者数据字段或具体临床业务功能。

需要先区分三个结果：一次任务完成、可复用机制改善、探索策略改善。对应的验证对象不同，不能用一次演示同时证明三者成立。

## 2. 两项研究的原始对象与可迁移边界

RRSI 研究固定底层模型权重、迭代修改 Agent harness。修改对象包括提示、工具、上下文管理和执行流程；主要约束包括变更预算、历史证据、泄漏检查、噪声与资源条件。实验覆盖编码、工作空间和工程设计任务。[RRSI 论文，§2–3、§4](https://arxiv.org/html/2609.24972v1)

Dream-RSI 固定发现 Agent、评估器及执行接口，修改探索策略。历史发现树提供已执行节点的结果，策略决定分支选择、并行与停止。选择保留当前策略，因而能保证所选策略在固定历史平均回放分数上不差于当前策略。[Dream-RSI 论文，§3](https://arxiv.org/html/2609.14858v1)

由此得到的 DX 设计推论是：RRSI 可以指导候选变更怎样提出和进入下一轮；Dream-RSI 可以指导实验怎样调度。两篇论文均未建立本项目真实临床任务的有效性，论文中的性能数值也不能直接转为 DX 验收指标。

截至本次核查，RRSI 有可检查实现；Dream-RSI 官方仓库的完整代码和复现脚本仍标为准备中。[RRSI 仓库](https://github.com/google-research/rrsi)、[Dream-RSI 发布计划](https://github.com/zhengkid/Dream-RSI#release-plan)

## 3. 先明确究竟在改进什么

| 对象 | 在 DX 中的含义 | 验证重点 |
| --- | --- | --- |
| 业务资产 B | 临床提示、工作流、工具适配，或 DX 应用代码与配置 | 当前变更满足任务要求，并通过对应回归检查 |
| 改进执行器 G | 分析问题、生成候选和执行修改的 Agent 及其 harness | 在未参与优化的后续任务上，质量或效率得到验证 |
| 探索策略 P | 候选方向选择、深化、并行、预算分配和停止策略 | 固定历史上的回放表现，以及新实验中的实际表现 |
| 评估契约 E | 任务要求、评分方法、阻断条件、有效性判定和评估器版本 | 能稳定区分已知合格、已知不合格和无法评价的结果 |
| 发布资产 R | 已通过对应评审、准备正式使用的资产组合 | 依赖兼容、集成检查、部署与回退 |

这些符号用于区分责任，不要求建设五套独立系统。

对代码开发，修好一个 bug 只证明业务资产 B 在该任务上改善。若声称“修 bug 的 Agent 变强了”，需要修改并比较 G，在独立任务上检验其可复用性。普通应用补丁搜索可以借鉴 RRSI 的约束，但不等同于原论文的 harness 自我改进。

临床工作流也一样：某个样例变好不自动说明机制能够泛化。持久化一条可复用提示或工具策略，且在独立任务中成立，才形成更强的可复用改进证据。

首期建议允许 B 受控变化，固定 G、E 和实验硬约束。G 与 P 可以版本化，但自动改写 G 放到后续独立研究流程；P 首期采用固定、可解释策略。

## 4. RRSI 的机制应如何迁移

### 4.1 小变更与证据记录

每个候选说明修改对象、改进假设、预期影响、依赖条件和实际版本差异。首期优先单一机制的变更；必须组合修改时，标记为组合效果，不把总收益归功于其中任一项。

原论文的组合编辑共享候选测量结果，这不是单个编辑的因果贡献证明。DX 若需要确认某个机制的独立作用，应补充对照或消融，而不是只读取编辑标签。[RRSI 论文，附录 C.2](https://arxiv.org/html/2609.24972v1#A3.SS2)

历史记录保留成功、失败、未采纳以及没有有效测量的候选。重复失败的假设降低优先级；当模型、工具或环境发生变化时，可在说明理由后重新检验，不把历史失败永久固化。

### 4.2 搜索采纳与正式发布分开

RRSI 的实现同时检查历史最佳分数附近的稳定性、成本条件与领域约束；处于噪声区间的候选还可能因降低成本或结构新颖性而获采纳，并非所有候选都必须显著涨分。[固定版本 selection.py，judge / cost_rule](https://github.com/google-research/rrsi/blob/be50316e1db05914068a973f322770ef08ed7ba1/rrsi/selection.py)

DX 应把“进入下一轮实验的候选”与“允许正式发布的候选”分开。新颖性可以支持继续研究，不能单独成为正式发布依据；关键约束不得由平均分或成本节省抵消。具体阻断规则需要业务与技术责任方共同确认。

简化后的决策顺序是：测量有效性检查 → 不可补偿约束 → 质量与回归检查 → 资源比较 → 搜索采纳决定 → 独立发布评审。没有合格候选时保留当前版本，这是有效的结束结果。

### 4.3 波动估计不是泛化保证

RRSI 代码支持根据基线重复运行或重采样估计噪声容忍范围。[固定版本 calibrate.py，calibrate](https://github.com/google-research/rrsi/blob/be50316e1db05914068a973f322770ef08ed7ba1/rrsi/calibrate.py)

对 DX，建议分别处理模型输出波动、模型评审波动和环境波动。样本不足时说明证据不足，不套用论文阈值；可在条件允许时使用同任务配对比较和重复执行。噪声阈值不能保证多轮自适应搜索不会过拟合，更不能替代独立验证。

### 4.4 失败与缺失不能被悄悄删除

RRSI 的评估保持预期试验数量，缺失试验不会从分母中消失；循环实现还会对较高缺失比例重试，并将持续无效的评估标记为无效。其成本比较在缺少 token 测量时使用退化处理。[evaluate.py](https://github.com/google-research/rrsi/blob/be50316e1db05914068a973f322770ef08ed7ba1/rrsi/evaluate.py)、[loop.py，_evaluate](https://github.com/google-research/rrsi/blob/be50316e1db05914068a973f322770ef08ed7ba1/rrsi/loop.py)

DX 应区分任务执行失败、环境不可用、评估器失败和结果缺失。按预先约定的政策重试或判为不可比较，保留原始记录；不能只挑选成功运行。成本缺失表示未知，不能据此宣称等成本或更高效率。

### 4.5 资源成本需要分账

建议分开记录业务版本的运行成本与产生该版本的实验成本。前者包括推理、工具与耗时；后者包括分析、提案、评审、执行、重复评估、人工判断与回放。避免用更多离线搜索换来少量运行节省，却只报告运行端下降。当前不预设具体数值或优化比例。

## 5. Dream-RSI 回放在 DX 中成立的条件

### 5.1 “精确”指已实现搜索空间内的记录

原机制按节点父子顺序揭示预存结果，策略只看到已揭示信息；没有被记录的结果不会由回放生成。其固定历史上的分数不下降保证不覆盖下一次真实执行。[Dream-RSI 论文，§3 Offline evaluation / Policy improvement and selection](https://arxiv.org/html/2609.14858v1#S3)

对 DX，应把回放结论表述为“在这些历史树、此类动作和此版本组合内的探索效率”。新任务、未记录分支或新执行机制需要新的执行证据。

### 5.2 不能把任意日志视为回放世界

可回放记录需要恢复：父候选快照、当时可见上下文、允许的动作、所选动作、实际结果、失败类型及消耗。若分支之间共享可变文件、服务状态或其他分支的新信息，重新排序可能改变生成条件；此时不能直接复用旧结果。

版本一致只是必要条件，还需满足依赖闭合与分支独立性。无法说明某节点依赖时，该轨迹仍可用于诊断，但不纳入相应的策略回放比较。

### 5.3 临床任务执行与实验调度是两种策略

首期回放建议面向改进实验调度：先尝试哪个候选方向、何时继续深化、何时停止。不要把这种结果扩展为临床工作流换一种工具调用或处理顺序后仍会得到相同结果；后者需要对应任务的重新执行与验证。

### 5.4 冷启动需要先产生真实实验树

先用固定调度策略，在开发或验证环境中实际执行、评估并保存分支。单条生产请求日志或一次成功结果不能提供充分的探索覆盖。模拟树可以验证回放引擎的逻辑，但不能证明真实搜索效率提升。

### 5.5 不可见结果必须由执行边界保护

回放策略通过受限接口取得已揭示信息，原始完整历史由回放器保管。不能一边要求策略不看未来，一边让其任意读取存有全部答案的文件。资源上限、超时与终止也由外部执行器强制实施。

### 5.6 回放比较本身需要防止过拟合

除策略开发用历史外，保留不用于策略生成的验证历史，并最终在新收集的实验中确认。若反复根据验证历史修改策略，该历史也成为开发证据，不能继续当作独立验证。样本不足时保持固定调度，先报告回放能力和覆盖情况。

## 6. 两套机制如何结合而不混淆版本

在一个实验周期内，固定任务契约、改进执行器 G、评估器 E、工具环境与资源规则。RRSI 式搜索产生不同业务候选 B；各候选本身可以不同，其快照正是树节点的一部分。之后冻结这批树，Dream-RSI 式回放仅比较探索策略 P。

若 G、E 或任务环境改变，旧轨迹仍是旧实验的证据，但不能默认代表新机制下的动作结果。应启动新的实验周期、建立新版本关联，并说明哪些历史还能用于比较。不能把“固定执行机制”误解为禁止搜索树内存在不同候选版本。

建议先按以下过程组织：

1. 固定任务和验证规则，建立基线。
2. 以固定 P 驱动候选生成、隔离执行和评估，积累树。
3. 将当轮树冻结为历史，检查依赖和可回放范围。
4. 对合格历史比较 P 的候选版本，保留当前策略作为参照。
5. 若证据支持，再将候选 P 带入下一轮开发／验证环境执行。
6. 分别检查新 P 的实验效率、最终 B 的质量以及发布资产的集成结果。

首期可完成第 1–3 步，并用预设策略验证第 4 步接口；自动生成策略及实际效率收益的结论应另设条件。

## 7. 共用架构与领域适配

| 逻辑部分 | 共用责任 | 领域特有部分 |
| --- | --- | --- |
| 任务与实验契约 | 基线、允许修改范围、输入引用、预算和终止条件 | 临床工作流要求或软件需求与缺陷说明 |
| 改进控制 | 分析、提出假设、候选组织、有限重试、搜索状态 | 分析指令、可编辑资产和修复操作 |
| 隔离执行 | 候选快照、作业生命周期、资源和权限限制 | 工作流执行器或构建测试环境 |
| 证据与资产 | 版本、来源、轨迹、结果与决策记录 | 原始记录格式、领域资产类型 |
| 评估编排 | 执行评估、有效性检查、回归和资源比较 | 各自评分、阻断规则与专业判断 |
| 候选选择 | 保留、拒绝、补充验证和终止决定 | 各领域不可补偿条件 |
| 回放与调度 | 合格历史、可见状态、调度接口和策略版本 | 可支持的动作集合及依赖约束 |
| 发布与回退 | 评审、依赖检查、发布清单和恢复记录 | 工作流配置发布或代码合入与软件发布 |

RRSI 已把执行、评分和轨迹处理委托给领域接口，提供了职责分离参考。[固定版本 Domain 接口](https://github.com/google-research/rrsi/blob/be50316e1db05914068a973f322770ef08ed7ba1/rrsi/domain.py)

这些模块可以先由单一编排服务、作业执行环境和资产存储实现。优先形成清晰的接口与责任，不要求首期建设复杂多 Agent 系统、分布式调度平台或完整中台产品。

新功能开发允许提出新增测试与评价要求，但先由相应责任方确认任务契约，再固定当轮比较标准。候选可以提交测试建议或开发测试；受保护的独立验收依据和既有回归要求不能由候选自行删改。这样既支持 feature 开发，又防止“修改检查方式就算通过”。

Git worktree 用于代码与版本工作区管理；需要的文件、网络、凭据与资源限制由隔离运行环境实现。模型候选不能修改任务契约、评估器或发布权限，限制应由执行系统落实。

临床模型、改进提案模型和评审模型可以使用相同或不同服务，角色是权限与责任分工。院内运行要求应覆盖提案、评审、日志和轨迹处理等整条链路；参考仓库默认的云调用配置不能自动成为 DX 部署假设。

## 8. 最小信息对象与三种状态

先定义系统对象关系，不定义患者数据字段：任务引用基线及契约；候选引用父版本与变更假设；一次执行引用候选、环境及输入；评估引用执行与评估器；决策引用证据与规则；发布引用资产组合及审批记录。

候选内容改变后产生新版本，不能继续沿用旧候选的测量结果。环境错误的重试与真正的新候选分别留痕。执行中断恢复时，已确认的结果不重复提交；外部动作是否可重试需由适配器明确。

必须分开保存三种状态：

- 执行状态：等待、运行、成功、失败、中断或无法完成。
- 质量决定：合格、不合格、证据不足、不可比较，或尚未评价。
- 发布状态：未申请、待评审、批准、发布或回退。

“执行成功”不代表“质量合格”，“搜索采纳”也不代表“允许正式发布”。失败候选的分析价值可以保留，但不能被误记为已验证经验。

两条最小代表过程可以使用抽象任务验证。临床工作流路径从已确认的任务契约出发，生成不同工作流候选并实际执行；某候选平均得分更高但触发约定阻断条件时，仍不能进入发布评审。这里验证的是选择行为，不预设具体临床规则。

代码路径从缺陷或新需求、基线代码与受保护的验收要求出发，生成补丁并运行开发测试、独立评估和回归；补丁满足单个样例却破坏既有约定时被拒绝。若还要把该补丁抽象为后续开发 Agent 的通用技能，另建机制候选并在新任务上检验，不能直接从一次修复推导出通用能力。

## 9. 三类记忆与两份版本清单

DX 建议区分原始实验记录、带条件的经验结论和已批准可复用机制。原始记录是依据；经验结论说明适用的模型、环境和证据强度；可复用机制是正式进入后续运行的提示、工具或规则。由记录到经验、再到正式机制，各有明确晋升条件。

DX 的改进经验与 CX 的患者长期记忆具有不同主体与用途。两者可以借鉴来源、版本、纠错与失效机制；不能因为技术底座复用，就把患者内容自动转为跨任务通用经验。数据授权变化时，应能定位受影响的输入、派生分析及后续使用范围，实际保留策略另行确认。

实验清单记录任务、基线、G、P、E、输入、工具环境和预算；发布清单记录实际运行需要的代码、工作流、模型、工具及知识规则依赖。P 通常属于实验来源，不必成为临床生产运行组件。

若代码与工作流分别优化，组合发布前仍需要集成回归。例如工作流依赖某工具输出约定，代码变更可能改变该约定；两项各自通过不等于组合有效。回退应恢复兼容资产组合。

## 10. 评估体系与结论强度

### 10.1 评估分层

| 层次 | 回答的问题 | 当前可做的工作 |
| --- | --- | --- |
| 流程验证 | 能否生成、拒绝、比较、停止、恢复及追溯 | 使用抽象任务与模拟资产验证 |
| 判断验证 | 评估器能否识别已知合格、不合格和缺失结果 | 构造正反例并核对规则与评审一致性 |
| 任务改进验证 | 某业务候选是否改善指定任务且无约定回归 | 在任务与评价依据具备后实际执行 |
| 机制泛化验证 | 复用机制是否帮助未参与优化的任务 | 独立任务／时间分割及固定基线比较 |
| 临床效果评价 | 是否改善真实工作或患者结果 | 在场景、数据和专业评价条件具备后另行设计 |

合成任务只证明相应框架行为。真实数据缺失时可以完成前两层的框架级工作，不能把结果升级为临床质量或临床效果结论。

### 10.2 搜索集、验证集与回归集

搜索集允许用于候选生成和反复测量；保留验证任务用于阶段判断；回归集保护既有明确能力。三者职责可以共享基础设施，但访问权限和使用记录应区分。被反复用来挑选和修订候选的验证材料，需要重新分类并补充新验证依据。

临床任务的具体专业评估要求暂不预设。模型评审可提供辅助证据，需要与可执行检查及必要的专业判断配合；不能把生成者与评审者使用不同角色名称当作评价独立性的充分证明。

### 10.3 有限预算与停止

为搜索设置外部执行的轮数、资源、重复失败和修复上限。允许的结束结果包括找到可评审候选、无合格候选、证据不足、环境不可用或预算用尽。结果包含原因和下一步依赖，不以无限重试替代问题解决。

论文的噪声、成本与新颖性规则是方法参考。首期采用可解释规则与明确终止条件，参数在实际任务、基线测量和资源条件具备后校准。

## 11. 首期与后置范围

| 范围 | 本期建议 | 理由 |
| --- | --- | --- |
| 共用任务、基线、候选和证据关系 | 必做 | 两类任务协作与追溯的基础 |
| 两类领域适配约定与最小代表路径 | 必做 | 验证共用底座的适用性；真实任务待资料具备后确认 |
| 候选隔离、权限和外部预算约束 | 必做 | 生成的修改需要受控执行 |
| 实际执行、评估有效性、回归与保留原版本 | 必做 | 没有这些环节就无法判定改进 |
| 搜索采纳、人工评审、集成发布和回退关系 | 必做设计并验证核心状态 | 将实验结果与正式使用连接 |
| 结构化树与有限回放验证 | 条件项 | 有合格历史时用预设策略比较；模拟验证单独标记 |
| 自动生成探索策略与新实验效率验证 | 后续扩展 | 依赖足够历史及可比较的评价 |
| 自动修改改进执行器 G | 后置 | 新增一层验证与版本问题，需独立证据 |
| 模型权重训练、开放式自修改、无人评审正式发布 | 后置 | 当前资料与框架目标不足以界定实施和效果 |
| 跨医院大规模推广、生产高可用与长期运营 | 后续确认 | 需要明确环境、范围和持续责任 |

对回放的三种交付状态要区分：能读取历史用于分析、能按约束重放已有探索、能证明新策略提高新实验效率。首期不把三者合并成“已实现 Dream-RSI”。

## 12. 顾问牵头的工作包与验证重点

| 工作包 | 顾问牵头设计与评审 | 工程团队实施 | 可审阅证据 |
| --- | --- | --- | --- |
| 任务与架构边界 | 确认两类任务、改进对象及模块责任 | 核对环境与执行适配条件 | 范围说明、对象关系与依赖清单 |
| 核心机制 | 实验契约、候选生命周期、判断与发布分离 | 状态流转、隔离、版本与轨迹记录 | 流程说明、代表任务过程记录 |
| 评估与选择 | 有效性、回归、比较和停止规则 | 评估适配、正反例运行、结果汇总 | 评估方案、失败分支和选择理由 |
| 历史与回放 | 判定可回放边界、版本兼容条件 | 历史读取、受限观测、预设策略回放 | 实际／模拟标记及覆盖说明 |
| 交接与发布 | 审阅组合依赖、回退及遗留条件 | 运行说明、验证包与恢复演示 | 最终设计、工程包、已知限制 |

首期必须验证的情形包括：无合格候选时保留基线；不合格候选平均分更高仍被阻断；评估无效不能当作候选胜出；重复提交不产生重复采纳；中断可恢复；更改候选后旧测量不误用；被隔离的任务不能越权读写；回放不能读取未来结果或为不存在的分支返回分数；分别合格的资产组合不兼容时不能直接发布。

框架验收关注这些行为是否按约定成立。实际收益、泛化与临床效果分别建立证据，不把“每次都找到更优版本”作为框架验收条件。

## 13. 下一轮需要确认的项目事实

1. DX 当前可获得的工作流资产、应用仓库、模型服务和既有测试评估条件。
2. 两类代表任务及其明确的输入、产物和评价依据；本轮无需具体患者字段。
3. 可修改资产的范围，以及任务契约、评估器和发布权限的责任方。
4. 是否具备结构化实验历史；其版本、分支依赖及数据授权能否支持回放。
5. 改进与评审模型可用的部署环境、工具访问和可观测性条件。
6. 顾问、工程团队、业务／专业评审方的交付与决策边界。

这些条件影响真实任务验证和后续自动化程度，不妨碍先完成共用架构、流程和模拟验证方案。
