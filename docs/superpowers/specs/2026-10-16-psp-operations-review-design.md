## 1. 目标与方案选择

服务人员进入项目服务台，先知道哪些事项需要处理、为什么、由谁负责，再进入已有联系、医生复核和教育流程。报告审核者打开一个修订，在同一处看懂上一版为什么退回、本版实际变了什么，以及本版还缺哪些签署。

三种实现路径：

| 路径 | 收益 | 代价与取舍 |
| --- | --- | --- |
| A：服务端只读投影，复用现有处理命令（推荐） | 规则集中，可用真实状态验证；不新增一套任务完成状态 | 需要为队列和版本比较各补一个明确的读取模型 |
| B：浏览器逐患者请求、临时拼出队列和旧版比较 | 初始代码较少 | 多请求带来混合 seed、授权变化和局部失败；不采用 |
| C：新建运营工单、催办和修订说明账本 | 适合后续正式运营系统 | 引入新的指派、完成、审计和迁移流程；超出本轮 |

采用 A。队列和对照都是已有业务事实的投影，不保存“已处理”勾选，不把界面提示当作新的业务证据。

## 2. 内部例外队列

### 2.1 入口与界面

在 `/clinic/projects/[projectId]/services` 的项目信息之后、成员名单之前加入“待处理事项”。保留现有成员管理与全部处理表单。

队列提供类型筛选：全部、问卷逾期、联系未成功、待医生复核、教育需帮助；并提供“与当前角色相关”和“仅看逾期”筛选。默认展示全部，避免切换角色后误以为其他事项已完成。

每项显示患者姓名、事项类别、事实原因、责任角色、已知期限、当前是否可处理和一个明确的下一动作。责任角色不冒充已指派的个人；仅在已有事实记录能支持时展示实际负责人。不能把预警的个案管理师承接人标成负责复核的医生。

同类事项保持稳定排序：可处理且已逾期的事项在前，其次其他可处理事项，最后因授权或状态受阻的事项；同组按期限、发生时间和稳定标识排序。无期限事项明确显示“尚未设定复核时限”，不以高风险联系时限代替医生复核时限。

宽窗口使用可扫描的分隔行；窄窗口按单项纵向重排，完整保留姓名、原因、期限和动作。筛选为原生可聚焦控件，有文字选中状态。空结果区别“当前无待处理事项”和“当前筛选下没有事项”。

### 2.2 时间与授权的共同规则

- 队列按读取响应中的 `serverNow` 判断当前状态，不用浏览器时间，也不借用月报 `cutoffAt`。页面标注“当前运营待办，截至……（上海时间）”。
- `dueAt < serverNow` 才为逾期，恰好相等不算逾期。未来分配的计划或未来才发生／入账的证据不参与当前判断。
- 计划取消、暂停或已完成，不列成开放计划。未加入的候选者不生成服务待办。
- 对已有未解决事项，成员暂停、退出、撤回服务授权或已不在项目服务期内时，保留受阻说明，禁用继续联系／复核的行动入口；不得引导绕过授权或把它当成已完成。
- 汇总授权独立：仅撤回汇总授权不阻断已获服务授权的内部服务。
- 队列条数是内部运营事项数，不是患者人数、事件次数或月报分母。界面明确“同一患者可能有多项待办”。
- 空间范围固定为当前项目和 seed；沿用内部服务台的身份验证，不向药企或患者新增此读取能力。

### 2.3 四类事项的形成与消失

| 类别 | 出现条件 | 消失条件与下一动作 |
| --- | --- | --- |
| 问卷逾期 | 本项目已分配的问卷计划仍开放，且已逾期 | 有效提交使该计划完成后消失；个案管理师进入患者服务记录核对并开展跟进，不代患者填答 |
| 联系未成功 | 已记录的真实联系结果为未接通、拒绝联系或渠道不可用，且对应计划／预警仍需处理 | 对相同目标有后续实际成功联系，或对应目标已按原流程完成后移除；进入原联系记录表单。拒绝联系提示先核对患者意愿，不默认再次拨打 |
| 待医生复核 | 预警属于该项目问卷链，已由个案管理师提交复核，当前仍处于待复核状态 | 只有原医生复核关闭流程成功后消失。新生成的未来跟进计划继续保持原有开放状态；预警关闭不表示症状改善 |
| 教育需帮助 | 明确反馈 `needsHelp=true`，且该反馈所关联的跟进计划仍开放 | 通过原联系流程完成该跟进计划后消失。教育本身反馈完成与帮助跟进完成分别表示；不回写患者“已理解” |

联系去重按事实关联处理：同一次联系覆盖两条预警，只形成一条联系未成功事项，列出仍待处理的关联目标；不会把它显示成两次联系。后续成功只解决它明确覆盖的目标，不能因同患者其他联系成功就清除全部失败事项。关联计划与预警状态仍分别保留；不同联系目标不因同名或同时间合并。

失败联系的先后以实际发生时间为主、账本顺序为同时间的次序；排除尚未发生／入账的记录。已有补录核验不改写原计划完成状态：若相关来源有补录，队列标明“原执行记录，存在待核验／已核验补录”，提供现有补录核验入口，不以补录推断原任务自动完成。队列与固定快照统计因此可能不同，说明二者用途。

教育跟进使用教育反馈事件中的明确 `followupAssignmentId`。仅有合成历史结果但找不到明确关联计划时，显示“历史帮助需求，需核对跟进记录”，不假造计划或断言已解决；该项仅提供核对入口。已取消／暂停的关联计划同样显示需核对的受阻状态，而不是清空帮助需求。

### 2.4 数据与组件职责

- 新增独立的只读队列投影模块，读取当前 `DemoStore`、项目与同一次读取时刻，输出类型、患者、目标引用、角色、期限、原因、受阻原因与导航目标。
- 在 `getInternalProjectView` 内通过现有身份校验后调用投影，一次响应返回项目成员和队列；不在浏览器发起逐患者读取。
- 新增队列组件，负责筛选与展示，不包含领域规则或新的写命令。
- 原患者服务区补充可定位的计划／预警锚点，链接能落到相关处理记录。临床身份仍由现有身份上下文决定，链接不授予或自动提升权限。
- 沿用 `usePspState` 的 seed、身份、请求失效与写入恢复规则。新增“刷新待办”用原读取流程，标注读取时刻；失败时展示错误与重试，不把旧队列标作最新。
- 待处理命令期间，队列导航不得绕过原有待确认／503 重试锁；403 或身份变化不得残留旧范围的患者事项。

## 3. 审核修订对照

### 3.1 入口与阅读顺序

内部月报工作台选中报告后，在审核操作之前展示“本版审核核对”。首屏顺序：本版状态与修订号 → 退回／修改要求 → 本次变化 → 本版签署 → 下一步；完整固定正文、来源、校验码和时间线继续可核对。

对照只比较当前报告与其明确的 `parentVersionId`，不是列表中的另一份“最新报告”。首版显示“初稿，无上一版可对照”。如果父版不存在或不属于同项目、seed 和报告批次，显示对照不可用，不回退到其他报告。

### 3.2 上一版意见与本版变化

上一版为内部审核退回时，显示退回角色、时间与原理由；上一版为客户请求修改时，显示该版客户修改意见及时间。两种意见清楚标记来源。当前版自己被退回时，也在本版状态区展示本版理由，不能把父版理由误标为本版已解决的结论。

本次变化分开核对：

| 维度 | 比较方法 | 表达 |
| --- | --- | --- |
| 冻结数据 | 快照标识、快照摘要和固定窗口分别比较 | 同一快照／更换快照；截止时点是否变化 |
| 受保护指标 | 按稳定的 `metricKey` 对齐，比较状态、单位、值、样本数、分子与分母及定义 | 指标未变或列出实际变化；新快照生成的 fact ID 不作为指标数值变化 |
| 下一期安排 | 按完整结构比较类别、负责角色、精确时刻和安排状态，保留重复项的次数 | 新增、移除、未变的安排并列，不能凭类别相同断言是同一项的修改 |
| 固定正文与规则 | 比较章标题、段落、模板、算法和保护版本 | 正文有变化／未变；规则是否变化，与快照变化分开 |

“快照已更换但可展示指标未变”是合法结果；“内容摘要改变”不能直接解释为指标改变。“已保护／未知／无适用”的变化按原状态展示，不能从内部精确指标推断被保护的差值。

指标对照仅使用两个固定报告中已有的保护事实；不重新计算历史指标，不加入患者级来源，不影响原固定正文和下载文件。大段内容或较长安排清单默认展开摘要、细节逐步披露；不是输出原始 JSON 或长篇自动生成解释。

比较只能证明字段变化，不能自动判断退回问题已充分解决。界面用“请核对是否回应上一版意见”，不用“问题已修复”作为自动结论。

### 3.3 当前签署与下一步

- 显示本版自己的提交、数据签署、医学签署；旧版签署只存在于旧版历史，不能带入新修订。
- 草稿说明“尚未提交”；提交后尚缺的审核角色从本版工作流得出。
- 当前角色已签署、另一角色未签署时，显示“本角色已签署，等待另一审核角色”；双签完成时显示“本角色审核已完成，等待项目经理交付”。
- 已交付显示等待客户验收；已验收显示查看交付与验收；退回显示由项目经理创建新修订；不是显示与当前角色无关的笼统失败条件。
- 当前来源授权受阻、存在更新修订、写命令未确认或 409 尚未核对时，仍按真实服务端 gate 解释；友好文案不能启用本来禁用的操作。
- 切换报告工作身份保留已选报告上下文，但旧身份响应与数据必须先失效，新角色重新读取同一项目／seed／报告；不能短暂露出旧权限的对照或复用旧写入。

### 3.4 数据与组件职责

- 新增服务端只读修订比较模块，接收当前版本、经归属核对的明确父版本及其意见事件，输出可直接展示的结构化差异。
- 在 `readInternalReport` 的现有授权校验后组合对照，作为内部详情响应的附加字段。同一次读取包含当前报告与对照，避免父版单独请求产生竞态。
- 新增核对组件，显示上一版意见、差异和当前签署交接；原审核按钮与 `ReportReviewPanel` 命令所有权保持不变。
- 原月报标题改为“PSP 月报工作台”，使名称覆盖已有草稿、双审核和交付职责；不改模板生成的固定正文。
- 药企报告读取、列表和导出仍使用其现有专用投影，不能复用内部详情响应。内部意见、未交付父版和内部来源不得被新增外发字段带出。
- 仅新增读取模型，不修改持久化 schema、报告摘要算法、不可变字节、签署绑定、CAS 或原请求回执。

## 4. 先后顺序与验收

按两项功能分别形成可验证的代码提交，最后补文档和端到端验收记录。详细实施计划在本设计核对后编写。

### 第一项：例外队列

1. 先写失败测试，覆盖四类事项、当前时间边界、项目与授权边界、联系多预警去重、后续成功仅清除已覆盖目标、教育明确跟进关联、补录只作提示、无依据的时限不能推断。
2. 实现投影、内部读取接入和服务台队列，再补筛选、空态、窄屏、目标定位和失败恢复测试。
3. 在隔离演示里真实操作：患者提交 → 未成功联系 → 成功联系 → 提交医生复核 → 医生关闭 → 教育仍需帮助 → 跟进联系完成。逐步核对队列增减、其他待办仍保留、服务记录未被队列修改。

### 第二项：修订对照

1. 先写失败测试，覆盖首版、同快照仅改安排、更换快照但指标相同、指标状态变化、重复安排、精确到毫秒的日期、无父版／错误归属、内部与客户两类退回、本版重新双签。
2. 接入内部详情及核对组件，补角色切换、旧响应丢弃、待确认写锁、409 手动核对及503原请求重试测试。
3. 在隔离演示里完成 r1 退回 → r2 添加安排 → 对照 → 数据签署 → 医学签署 → 交付 → 药企验收，确认旧报告和文件字节保持不变，药企读取不含内部意见与对照字段。

### 共同验证

- 运行针对性领域与组件测试，再运行全量单元测试、lint、TypeScript 检查。
- Next 端到端覆盖新增交互；Worker 安全构建和隔离 Worker 端到端确认附加读取模型兼容现有运行环境。
- 代表性窄窗口与桌面截图核对：姓名、期限、长退回理由和完整结构化安排不被截断；状态不只靠颜色；关键操作可键盘聚焦。
- 不部署、不推送，不重置用户当前 `localhost:3000` 演示；测试使用独立运行实例。
- 提交前记录准确通过结果和仍存在的限制；只有实际验证通过的内容标记完成。
