# PSP Demo 产品体验与药企业务价值评审

历史基线说明：以下为 UX 改造前的评审，评分、问题和“暂不编码”均指当时状态。后续已获用户授权实施 UX Task 1–6；最终范围和结果见 [验收报告](../../docs/superpowers/sdd-ledger/2026-10-15-psp-client-experience-report.md)，不将本次初评评分当作改造后的复评分。

日期：2026-10-15。目标：components/psp 与药企 PSP 页面。基于本轮真实 UI 操作到“客户已验收 · 修订2”、两项独立只读评估和现有商业方案；本轮未新增外部市场、法规或临床研究。只做分析，不编码、不改变项目演示状态、不提交代码。

## 核心判断

现版已证明项目服务事实可以形成有来源、有人工责任、有固定版本的交付。下一轮最大提升空间是：药企负责人能快速理解购买范围与履约情况，审核者能快速看懂修改，项目经理能据此推进下一件事。当前需要演示者解释较多，界面中的核对材料比业务判断突出。

应继续保留三个基础：一次联系覆盖两条预警仍只计一次；关闭与未来任务、教育打开与反馈、交付与验收分别记录；固定正文、当前授权及双签/修订相互约束。

## 视觉与证据判断

没有明显装饰性AI风格问题。现有白底、系统中文字体和克制洋红色可以沿用，优先调整信息层级、状态语言与任务交接。

独立CLI检测扫描components/psp及app/pharma：25个TSX、1个TS，exit0、0条规则命中、无误报。静态正则扫描干净不代表体验或业务价值已经优秀。只读浏览器补充了扫描未捕捉的真实问题。

本次客户报告在独立1280×720视口：页面高5674px；正文从y1014开始；客户反馈从y5365开始。有7章、40项指标、57段正文。40项中5项数值可展示，26项受保护，9项无适用；4条相同定义分别重复13、11、8、4次，覆盖36项指标。这是信息组织问题，不能据此降低保护阈值，或把受保护/无适用解释为零。

## 五项体验优先问题

### P1：客户页先呈现核对信息，业务结果出现太晚

客户首屏主要显示时间、两段64位校验摘要、模板/算法/保护版本及导航；真正服务结果在后面。建议按“本期范围与交付摘要—可评价结果与证据限制—下一期安排—完整指标—核对资料”组织。可评价内容只能来自允许外发的固定保护事实；隐藏的数值不能借红黄绿、结论句或AI总结重新泄露。

指标按业务问题分组，可将重复说明放入口径展开。问卷小样本保护保留，不能为图表好看改种子或放宽阈值。

证据：components/psp/PharmaReport.tsx:24–27；ReportPreview.tsx:15；本次只读DOM。设计动作：$impeccable shape / distill。

### P1：已验收与“模板草稿，待人工审核”并置

页面顶部已验收，固定正文仍突出旧标记；“正文摘要”实际为校验串，也容易被理解为业务摘要。界面解释保留生成时标记仍要求客户自己消解矛盾。

建议当前状态作为唯一主状态，历史生成标记放归档说明；核对码进入可展开证据区。已交付文件不能回写，必要时附独立交付封面/凭证。今后生成的固定正文可采用不会随流程过时的说明，签署及验收继续单独记录。内部“固定报告草稿”标题也应与实际月报工作台职责匹配。

证据：ReportPreview.tsx:14；PharmaReport.tsx:24,27；lib/psp/reportTemplate.ts:49。设计动作：$impeccable clarify。

### P1：审核者缺少针对当前修订的核对包

长页面并置创建、快照、父版本、版本选择、操作、时间线、正文与内部来源；切换模拟角色后还需重新选择报告。审核者要记住旧版意见，再找新版修改。双签完成后某审核角色的“下一步”仍显示签署条件限制，缺少“本角色已完成，等待项目经理交付”的交接说明。

建议内部审核视图先展示退回理由、本次修改、是否更换快照/指标、待补签角色和下一动作。本次r1→r2仅补下一期安排，可直接说明“正文安排已变，快照与指标未变，新版仍需双签”。内部意见和未交付版本资料不能直接移到药企端。切角色可以保留项目/报告上下文，权限和新读取仍须重新核对。

证据：ReportDraftDesk.tsx:40–49,62–69,80–96；本轮真实操作。设计动作：$impeccable shape / layout。

### P2：患者多条同名复评不易理解

患者计划同时出现两条同名同时间的PSP复评，以及临床随访计划中的两条复评。真实来源是两条预警，不能直接删除其中一条。

建议写明复评目的、谁会联系、时间、患者需准备什么，并交代两条任务的关系。只有医生确认属于同一次随访时才可聚合呈现，保留各自来源和完成状态，不能凭同名同时间推断为同一次预约。未来复评继续待办，关闭预警不表示症状改善。

证据：patient-plan.png；components/psp/Common.tsx:18；app/patient/plan/page.tsx:15–23。设计动作：$impeccable clarify / shape。

### P2：主次操作与就地说明可以更清楚

刷新、下载、切换视角和业务操作共用相近描边样式；报告有两处刷新。日期无效时使用整组通用说明。“时间需晚于当前演示时间和项目截止”中的项目截止容易与项目结束混淆。

建议每个状态突出一个主动作，其余作为辅助操作；字段旁明确上海时间、观察截止与项目结束的区别，指出具体哪条安排有问题。自动化工具填日期/等待错误精确按钮名的困难属于本轮操作工具问题，不应冒充产品缺陷。

证据：Common.tsx:5；ReportDraftDesk.tsx:46–49；PharmaReport.tsx:25,39；ServiceWorkflow.tsx:32。设计动作：$impeccable clarify / polish。

## 角色与情绪路径

药企首次读报告：需要先知道本期交付和需要确认什么，当前容易被校验串与草稿文字打断信任。
项目经理/个案管理师：一次联系多预警是优势；成员展开和长报告之外，仍需要按到期未完成、联系失败、待复核、教育需帮助组织的任务队列。
患者：收到回应和未来任务能形成安心感，多条同名复评会重新带来不确定。

认知负荷主要在单一焦点、视觉层级、一次一个决策、跨区记忆及逐步披露，约5项明显不足。跨角色人工责任属于业务必要复杂度；裸ID、反复定位和重复说明是可减少的额外负担。未做真实手机用户或完整无障碍实测。

## 药企业务价值的五个提升方向

1. 购买与履约摘要。项目概览已有范围、周期、联系目标、授权人数、交付列表；尚没有合同交付物—本期承诺—允许披露的实际—例外处理—下个里程碑的一屏表达。先用明确标为演示约定的服务包和交付清单，真实服务频次/SLA/采购与验收方仍待客户确认。不能把内部18人和外部14人并列给药企，也不能让隐藏结果变成可推断绩效。
2. 例外驱动的内部运营。复用已有事实形成待办队列，显示责任角色、期限、原因和下一动作；药企只看保护后的项目级信息。通过一个联系未接通/待复核/教育需帮助事项展示持续运营，保留真实未完成，不为演示补造结果。
3. 月报业务摘要。先呈现可评价的执行结果、证据限制、下一期安排及需要客户协调的事项，再给完整指标。隐藏/未知不能通过摘要或红黄绿推断好坏。无可比基线时不输出环比提升；跨期比较还需范围/算法/窗口可比与联合披露检查。
4. 客户可流转的验收证据包。已有固定文本/HTML、签署和客户反馈；可整理项目/期间、交付物、允许输出口径、签署、当前可读状态及下一期安排的清单。内部r1→r2差异先服务审核者；外部只披露获准交付内容。验收确认范围与交付，不等于所有KPI达标。PDF封面和版式可后续完善，优先确认客户实际收件格式。
5. 可测量的AI辅助案例。现月报是确定性模板，医生助手有真实演示草稿。选择一项随访整理或交付准备任务，呈现输入事实、草稿、人修改、复核与实际执行，分别记录准备、审核、返工时间。固定演示时钟的0小时耗时不能测效率；不能预设省时比例、毛利、患者获益或ROI。患者是否收到有意义反馈及是否理解下一步应成为体验价值，而非默认持续用药越久越好。

## 路径选择与建议顺序

路径A（推荐）：药企能看懂和验收，先做项目履约摘要、客户报告分层/状态澄清、交付清单及内部修订差异。直接改善面向药企的讲解与交付可信度。
路径B：先强化项目经理日常运营，增加例外队列和患者下一步表达。适合下一步要评估团队能否持续执行项目。
路径C：扩展新AI/研究业务菜单。当前缺真实客户验收和工时基线，优先级较低，不作为本轮建议范围。

建议先做A的窄范围产品设计，再补B；AI效率案例在有可比较的人工样本后推进。临床/项目分母、授权、固定快照、不可变交付、双签等已验收规则继续保留。

未来检验改进是否有效，可让未参与开发的人不看脚本，说明购买范围、阶段交付、可判断结果及下一步；让审核者在同一屏找到退回原因与本次修改；让患者说明自己需不需要到院或等谁联系。这是建议的验证任务，尚未实际执行。

## 需要的真实业务输入

一份脱敏项目服务范围/SOW、一份实际月报与验收样张、一项人工交付任务的工时与修订记录。它们用来确认首个采购/验收方、交付格式、目标口径和成本，不能从当前演示假定客户已经认可。
